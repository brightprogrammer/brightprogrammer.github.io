Some Background

I got my eyes on Rizin after a friend told me there’s a project that I might be interested in. I was working on my own x86 disassembler at that time and I wanted to convert that to an Intermediate Language that I wanted to create. This language would then be used to analyze binaries and decompile it. I was able to write a basic (very bad, but superb working, now that I see it) disassembler. I was still very very far away from creating the Intermediate Language of my dreams and I started reading books on program analysis, thesis papers on decompilation and SSA etc… just to give me enough headstart before I start the real work. All this was good but I still lacked one thing! “Experience”. I had no experience in working with an IL before and from experience I can tell you this :

“If you every try to create something new, from scratch, without any prior knowledge, you will end up doing it iteratively!”

Why iteratively is bad in this case? Well because creating a whole new IL is a big thing. It’s a mathematical abstraction (langauge) in the first place of some very well defined language. You’ll be able to do it “eventually” but this will be so long in time that you’ll feel you wasted too much of it! You could have just learned to work with an already present IL, learned how it works from inside out and then tried creating your own, but you didn’t and now you failed. You atleast need a formal course at the minimum if you don’t want to follow the former approach.

Since I knew this, I used to discuss this with my friend and then he pointed out one day that Rizin has it’s own IL. A new one and they are looking for contributors to work on it! I knew nothing about how rizin worked before I started working on it. That’s how all other contributions happen. One day you don’t know anything and another you start learning things.

Contribtions/Microtasks

My first PR in Rizin is on March 10 2023 (iirc) with a microtask that was mentioned in Rizin’s 2023 GSoC page. This is about 1 month before proposal submission deadline and about two months before getting selected. What started out as a very very very basic refactoring, turned out to be a very big one! You can judge that by the size of that PR. I expected it to be over in about a week but it continued for about a month. But I now see why there are microtasks. I easily separates those who can work on the project and those who are not able to or don’t have enough motivation. During this microtask, I learned development coding styles and got to interact with my mentors. This was the first time I was looking at how compiler/interepret grammars can be written in code because Rizin has it’s own RzShell language now to parse your commands. The grammar will help another tool, tree-sitter map from commands to the corresponding handler. This method of handling commands is highly scalable and is very easy to maintain. I got chance to re-implement the command syntax for a complete family group! This was huge! I got a change to play with the grammar file itself! I wrote some regression tests too.

So if you are a GSoC aspirant then I’d recommend you to start working on your project atleast one to two months before you actually submit your proposal. Even if your PR isn’t merged yet, you should start writing your proposal and discussing it with your mentors! It’s very important because you can plan your work timeline with them. Rizin mentors explicitly asked us fellow contributors to show them their proposals so they can review and give feedback early.

There are contributors out there who’ve started working about 6-7 months before submission deadline. Early bird get’s most of the benifits. Early contributors already have a good level of bonding and communication set up with the development commnunity and they are likely to be selected in preference over you! There are still lots of factors involved but yea, consider this as a rule of thumb.

Current Work

My current work revolves around RzIL (Rizin Intermediate Language). I already wrote a blog post about it here in which I explained how uplifters are written. It’s better if you read it and come back to this post but I’ll try to re-explain things in a better way this time because I have little bit more clarity.

Syntax & Semantics

In easy words “syntax” deals with how a language is written. I’m talking about languages in general here so you can compare it with your native language too! So, “syntax” is the grammar! It only deals with how it must be written. A statement (or sentence) might be written correctly (syntactically correct) and still have no meaning at all! Now if you pause for a moment here and think about what we mean by the word “meaning” itself?

If I ask you to “read this blog post completely”. What do I mean by it? Don’t pfffh me by repeating the sentence again in your head. Think about it! What does it mean? It means you should take the “action” that is assigned for reading! or in other words, you must do certain “sequence” (not a set) of operations that we’ve assigned to the word “read”. What does completely mean? “completely” will determine how long it’ll take you to “read” it and how you should “read” it! Every word in that sentence has a “meaning”.

So, we an easily extrapolate this simple idea to the fact that every language evaluates to some set of actions/operations that the “understanding object” must do. This object we are talking about would be able to “understand the meaning” of the statements formed in the selected language and take actions accordingly!

Introducing Intermediate Languages

There can be infinite number of languages out there (mathematically). To understand each and every single one, you need to understand it’s grammar first and then understand what each word/alphabet means, i.e. how you can map these words/alphabets to a “sequence” of operations. This is a very big, very less scalable and not much maintainable task. Why? If you have n languages then you need to understand those “n” langauges! What if you only had to understand one language? We can write a translator from every other language to the language that you understand the most.

In this case we are dealing with CPU architectures and their assembly language. I think I know x86 the most as compared to other architectures, so if I can write a translator to convert all other languages to x86 then voila! My task is done and I can easily study and analyze them! Simple? No! When you translate a language to another, your main goal is to capture it’s semantics properly! What if your langauge didn’t have a word or a sequence of words that evaluate to same semantics as target language? It’s true, this is possible in all languages! Even the ones we speak and read!

So, we need a language that can capture the sematics well and a language the we understand it best possible way!. Now we are engineers and we want automation everywhere so we need a language that can be processed by computers easily too! This is where Intermediate Languages come in. Since we create these languages, we know exactly how they work and if need comes, we can extend them too! Remember the end goal here is to capture the semantics in best way possible!

Rizin Intermediate Language

In computer world, all actions can be broken down into two types :

  • Pure actions, i.e. they are pure values and hence they don’t affect the state of system.
  • Effect actions, which by name means they change the state of system and hence affect the state.

Note that both are operations that “ANY” CPU performs! This is a very high level description but if you subdivide these actions to further types, you’ll be able to capture semantics of almost any language out there! Even English, if you extend it enough! XD.

My Work This Summer

I need to write uplifters (convertors) from MIPS assembly language to Rizin intermediate language. What do I mean by uplifters? Well as I said, RzIL is easier and at a high level from MIPS low level assembly language. MIPS langauge precisely defines what the machine will do but RzIL will tell the RzIL VM what the machine will do and the VM will try to emulate the same thing inside itself.

First keep in mind these typedefs :

typedef RzILOpPure Pure;
typedef RzILOpEffect Effect;

Bool and BitVector are Pure values too, so you can use them interchangeably, but it’ll be more readable like this.

My work began with reading the introductory manual and understand register types, names, count etc… and different types of operations. I’ll be using Capstone to process the assembly using structs and enums. Capstone has enums defined for registers and differnt instructions that I can use to map from enum to it’s corresponding name! So I created an array to map register enum to register name and instruction enum to corresponding uplifter function. Recall the map I was talking about in “Introducing Intermediate Languages” section. This is that map! Convert from MIPS to RzIL using this map.

// char*

// Pure*
#define IL_REG_F(idx) VARG(REG_F(idx))

// returns Pure*
#define REG_NAME(regenum)    cpu_reg_enum_to_name_map[regenum]
#define IL_REG_OPND(opndidx) VARG(REG_OPND(opndidx))

So when I do REG_R(31), I’ll get the string "r31" and when I do IL_REG_R(31), I’ll get the Pure value for RzIL. VARG let’s the VM know that it’s a global variable. Similarly there’s VARL to let it know that this is a local variable.

And now we can map them using a simple function :

/**
 * Mips lifter dispatch function.
 *
 * \param cs_insn
 * \param pc Instruction address of current instruction.
 * \return Valid RzILOpEffect* on success, NULL otherwise.
 **/
RZ_IPI Effect *mips32_il(RZ_NONNULL cs_insn *insn, ut32 pc) {
	rz_return_val_if_fail(insn, NULL);

	MipsILLifterFunction fn = mips_lifters[INSN_ID(insn)];
	if (fn) {
		Effect *op = fn(insn, pc);
		return op;
	}

	rz_warn_if_reached();
	return NULL;
}

I also need to define the initial config of VM eventually but I’ll describe them in some later blog post because I haven’t dealt with them up until now. This config will define the initial state of VM.

The next task is to go through the ISA manual, instruction by instruction and convert the instruction to equivalent RzIL effect sequences. Up until now I’ve written uplifters for ADD instruction and ADD instruction family, BRANCH and corresponding family and JUMP and corresponding family and some others too. I took printout of these manuals and I’m using them and the PDFs on my laptop together to work efficiently, although I do believe it can be done without the printouts.

/**
 * Add word.
 * Format : ADD rd, rs, rt
 * Description: GPR[rd] <- GPR[rs] + GPR[rt]
 * Exceptions: IntegerOverflow
 * */
IL_LIFTER(ADD) {
	// get operand registers
    char *rd = REG_OPND(0);
	Pure *rs = IL_REG_OPND(1);
	Pure *rt = IL_REG_OPND(2);

	// perform addition and set to destination register
	BitVector *sum = ADD(rs, rt);
    Effect *set_rd = SETG(rd, sum);
    
	// Bool *overflow = IL_CHECK_OVERFLOW("rs", "rt", REG_OPND(0));
	Effect *update_status_op = NOP(); // TODO: set status flag

	return SEQ2(set_rd, update_status_op);
}

It’s easy to understand that in first three lines I’m getting the first three operands in their order. Only for GPR[rd] I’m getting the name in a char* but for others I’m getting a VARG(name). Then you see there’s an ADD which is a pure operation because it evaluates to a value! It is not changing state of VM (yet) and then we set the sum to GPR[rd]. This is an effect because we made a change to state of the VM. I haven’t yet figured out how I’ll update the overflow status because in MIPS there are no such flags. It just straightaway throws exceptions! My mentors suggested me to store it somewhere instead of caring for exceptions at the moment.

Also, note that eventually the ADD operation in MIPS got converted to a sequence of Effect operations in RzIL. This is what capturing semantics in an intermediate languages look like!
