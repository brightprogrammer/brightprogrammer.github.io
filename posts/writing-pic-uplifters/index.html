Writing Pic Uplifters
Damn It's Hard!

published on Fri, Apr 21, 2023 | 5 minutes read

  • Posts
  • Writing Pic Uplifters

In last post we went through the general reference manual. Turns out (after going through some datasheets), it’s better to divide the whole IL uplifting process into families like :

  • PIC16FXXXX
  • PIC18FXXXX
  • PIC32FXXXX (completely different device!, take a look)
  • etc…

Why? Well because I went through the datasheets and it looks like the reference manual we referred to is outdated and new devices were added to family with more memory banks! I noticed some datasheets specifying that the given device has 32, 64, 128 etc… memory banks! The reference manual states there are only 4 memory banks in each device in family. Well, I did find some devices with 4 memory banks but now I think that since it’s hard to find which device belongs to which family (since manual states devices starting with name pic16f but clearly new devices don’t follow the manual), it’s better to split them based on device initials instead of mid-range, base-line and high-end.

Keep in mind that we eventually want to uplift all Mid-Range devices even though it doesn’t seem like so atm. We’ll need datasheets of PIC16CXXXX etc… too but let’s worry about those later. For now, we’ll uplift only PIC16FXXXX devices.

Now I just have to go through these datasheets one by one and get their memory map and instruction set. One more advantage of this process is that we can get exact idea of which instructions a chip supports and which ones it doesn’t. This might help improve analysis by detecting faulty instructions.

Improvising Previous Plan

Previously I was setting register map like a string array and assumed that it’ll be same for all devices but now I think, since register types are same across each of these devices (not verified) and only memory map and supported instruction set is changing (verified) we can create an enum of register types, create a lookup table to map from these enums to their string values and then define the memory/register maps using these enums. This way to add new devices we just need to add new memory maps! Ez Pz af.

Here’s the register enum types :

/**
 * \file : regtypes.h
 * \brief : Defines the various reigster types supported by the PIC16F family
 * and a lookup table to map from these register types to their string names.
 * */

#ifndef RZ_PIC_MIDRANGE_PIC_REGTYPES_H
#define RZ_PIC_MIDRANGE_PIC_REGTYPES_H

// clang-format off

/**
 * Instead of storing strings in file register map,
 * it's better to store enums in order to save memory.
 * */
typedef enum pic_midrange_reg_type_t {
    REG_INDF,
    REG_TMR0,
    REG_PCL, /* lower byte of PC register */
    REG_STATUS, /* status register */
    REG_FSR,
    .
    . /* (truncated, more registers here) */
    .
    REG_EEDAT,
    REG_EEADR,
    REG_SRCON,
    REG_BAUDCTL,
    REG_ANSEL,
    REG_ANSELH,
    REG_EECON1,
    REG_EECON2,
    REG_RESERVED,
    REG_FREG, /* normal indexed file register */
    REG_UNIMPLEMENTED, /* unimplemented registers are read as 0 */
} PicMidrangeRegType;

/**
 * Map from reg enums to reg names
 * */
const char* pic_midrange_il_regnames[REG_UNIMPLEMENTED + 1] = {
    [REG_INDF]          = "REG_INDF",
    [REG_TMR0]          = "REG_TMR0",
    [REG_PCL]           = "REG_PCL",
    [REG_STATUS]        = "REG_STATUS",
    [REG_FSR]           = "REG_FSR",
    .
    . /* (truncated, more registers here) */
    .
    [REG_EEDAT]         = "REG_EEDAT",
    [REG_EEADR]         = "REG_EEADR",
    [REG_SRCON]         = "REG_SRCON",
    [REG_BAUDCTL]       = "REG_BAUDCTL",
    [REG_ANSEL]         = "REG_ANSEL",
    [REG_ANSELH]        = "REG_ANSELH",
    [REG_EECON1]        = "REG_EECON1",
    [REG_EECON2]        = "REG_EECON2",
    [REG_RESERVED]      = "REG_RESERVED",
    [REG_FREG]          = "REG_FREG",
    [REG_UNIMPLEMENTED] = "REG_UNIMPLEMENTED",
};

// clang-format on

#endif // RZ_PIC_MIDRANGE_PIC_REGTYPES_H

Then the register/memory map is defined in a separate header file for each device type like this :

/**
 * \file : pic16f882.h
 * \brief : This file describes the memory map of PICF16882 device in PIC16F family.
 * */

#ifndef RZ_PIC_MIDRANGE_PIC_MEMMAP_PIC16F882_H
#define RZ_PIC_MIDRANGE_PIC_MEMMAP_PIC16F882_H

#include "regtypes.h"

// clang-format off
PicMidrangeRegType pic16f882_reg_map[] = {
    /* BANK 0 */
    REG_INDF,                   /* 0x00 */
    REG_TMR0,                   /* 0x01 */
    REG_PCL,                    /* 0x02 */
    REG_STATUS,                 /* 0x03 */
    REG_FSR,                    /* 0x04 */
    REG_PORTA,                  /* 0x05 */
    REG_PORTB,                  /* 0x06 */
    REG_PORTC,                  /* 0x07 */
    REG_UNIMPLEMENTED,          /* 0x08 */
    REG_PORTE,                  /* 0x09 */
    .
    . /* (truncated) */
    .
    REG_CCPR2L,                 /* 0x1b */
    REG_CCPR2H,                 /* 0x1c */
    REG_CCP2CON,                /* 0x1d */
    REG_ADRESH,                 /* 0x1e */
    REG_ADCON0,                 /* 0x1f */
    REG_FREG,                   /* 0x20 */
    REG_FREG,                   /* 0x21 */
    REG_FREG,                   /* 0x22 */
    .
    . /* (truncated) */
    .
    REG_FREG,                   /* 0x7b */
    REG_FREG,                   /* 0x7c */
    REG_FREG,                   /* 0x7d */
    REG_FREG,                   /* 0x7e */
    REG_FREG,                   /* 0x7f */

    /* BANK1 */
    .
    . /* (truncated) */
    .

    /* BANK 2 */
    .
    . /* (truncated) */
    .

    /* BANK 3 */
    .
    . /* (truncated) */
    .
};
// clang-format on

#endif // RZ_PIC_MIDRANGE_PIC_MEMMAP_PIC16F882_H
