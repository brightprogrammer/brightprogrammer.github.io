General Learning Plan

Since, this is the first time I’m writing uplfiters, I’m laying down a path that I think I must follow to accomplish this task. I actually took handwritten notes (before I had this blog) in order to map the path properly. I planned this path in a much general way. You can used this to path, remove PIC from everywhere and insert any alien architecture you want to work and this should work more or less the same way! Also, if I plan to change the path sometime in future, instead of editing it here, I’ll recreate this somewhere else and add a reference here so you know what changed and why I changed it! This is good for people like me who wanna lern the process of learning itself.

For Learning The Architecture
  • How PIC works? Where is it used? This includes things like taking a look at it’s assembly even before you understand the meaning of instructions and their syntax. Trying to know terms (knowing meanings is not necessary at all!) such as “registers”, “memory banks”, “pages” etc…
  • Understanding Memory Model. This step must be taken before you try to understand any instruction.
    • Memory Model
      • Von Neumann? (like x86)
      • Harvard? (like this)
      • Other (that I don’t know about yet?)
    • Endianness (if Von Neumann like architecture)
    • Registers
      • Names
      • Sizes
      • Is there any calling convention
      • Meaning of registers (every architecture has some special registers and some general registers for scratch operations).
      • Some other architecture specific information you can find, like in PIC there are memory banks which is not present in x86. Even if it is present, it is not programmatically differentiable to any public priviledged user.
    • Try understanding some instructons with help of this new gained information/insights
    • Memory Addressing Modes Some architectures have different addressing modes for different purposes.
      • Direct Addressing Modes.
      • Indirect Addressing Modes.
    • Do I need to understand Timers/Oscillators etc…?
      • How to get time in a register?
      • How does instruction clock cycle work? In PIC it’s divided into 4 cycles that run parallely. See Instruction Pipelining.
    • Are there exceptions & interrupts?
      • How do interrupts work? Almost any architecture that handles some type of external input must have support for interrupts and a way to handle them.
      • How do exceptions work? Almost any architecture that supports arithmetic operations must support exceptions and a mechanism to handle them.
    • How does device reset work?
      • How many types of reset are there? First one you already know is POR (Power On Reset).
      • What is state of registers after a reset?
      • Is there any way to know which type of reset occured? (Using STATUS register on PIC)
    • Instruction format.
      • General instruction syntax/format
      • RISC instruction sets will have fixed sized instructions which they generally call Instruction Word,
      • CISC instruction sets (like x86) are generally hard to understand because of their hacky modifications in future versions to support new instrructions.
    • Program Counter
      • Size of program counter.
      • Working. Like in PIC, to address to different pages you need to specify the page index in PCLATH register. This means you need an understanding of addressing modes.
        • Direct Addressing Mode.
        • Indirect Addressing Mode.
        • Any other new Addressing Mode.
For Writing Uplifters
  • Start understanding the semantics of each instruction because good ILs capture the semantics of an instruction in an as good as possible way. Better semantics capturing means more knowledge about architecuture and easier simulation.
    • For instructions like ADD DST_REG, SRC_REG1, SRC_REG2 the semantics would be :
      • Read value from SRC_REG1
      • Read value from SRC_REG2
      • Perform addition operation of SRC_REG1 and SRC_REG2
      • Store the result in DST_REG
Important Note

This need not be the way actual CPUs implement instructions because by capturing semantics, we need only capture detail in such a manner that it not only closely resembles the actual working but also allows us to directly emulate each operation in each instruction.

  • It might happen that internally they can directly use registers to operform addition. They just need to read one register and somehow directly add it to the other register.
  • It might also happen that CPU reads one register to a `Working Register` and then add the value in second register to the value in Working Register and then move this value to destination register. If destination is the Working Register itself, then it just skips this part.
In both the cases, if we follow the usual procedure, it'll still be very close to actual working of instruction.

Each of the above steps including the instruction itself is an operation in RzIL (RzILEffectOp).

  • Get to know the register model in a more concrete way because we need to define a function that’ll return RzAnalysisILConfig for every architecture we uplift that represents the memory model of architecture RzIL is going to emulate. This includes knowledge of things like :
    • Program Counter
      • Size (in bits)
    • Is the architecture Big Endian?
    • Registers
      • Size (in bits)
      • Number
      • Special Names?
      • General ones?
    • Memory
      • Size (in bits)
    • Labels (for operations like : interrupt, syscall, hooks, callbacks etc…)
    • Initial valus of registers

/**
 * \brief Description of the global context of an RzAnalysisILVM
 *
 * This defines all information needed to initialize an IL vm in order to run
 * in a declarative way, in particular:
 *
 * * Size of the program counter: given explicitly in `pc_size`
 * * Endian: given explicitly in `big_endian`
 * * Memories: currently always one memory with index 0 bound against IO, with key size given by `mem_key_size` and value size of 8
 * * Registers: given explicitly in `reg_bindings` or derived from the register profile with `rz_il_reg_binding_derive()`
 * * Labels: given explicitly in `labels`
 * * Initial State of Variables: optionally given in `init_state`
 */
typedef struct rz_analysis_il_config_t {
	ut32 pc_size; ///< size of the program counter in bits
	bool big_endian;
	/**
	 * Optional null-terminated array of registers to bind to global vars of the same name.
	 * If not specified, rz_il_reg_binding_derive will be used.
	 */
	RZ_NULLABLE const char **reg_bindings;
	ut32 mem_key_size; ///< address size for memory 0, bound against IO
	RzPVector /*<RzILEffectLabel *>*/ labels; ///< global labels, primarily for syscall/hook callbacks
	RZ_NULLABLE RzAnalysisILInitState *init_state; ///< optional, initial contents for variables/registers, etc.
	// more information might go in here, for example additional memories, etc.
} RzAnalysisILConfig;

Where, RzAnalysisILInitState is defined as follows :

/**
 * \brief Description of an initial state of an RzAnalysisILVM
 *
 * This may be used by an analysis plugin to communicate how to initialize
 * variables/registers for a clean vm.
 * Everything unspecified by this may be initialized to anything (for example
 * whatever contents the RzReg currently has).
 */
typedef struct rz_analysis_il_init_state_t {
	RzVector /*<RzAnalysisILInitStateVar>*/ vars; ///< Contents of global variables
} RzAnalysisILInitState;

RZ_IPI RzILOpEffect *rz_pic_midrange_il_op(RZ_NONNULL RzAnalysis *analysis, RZ_NONNULL RZ_BORROW RzAnalysisOp *op, ut16 instr) {
    // get opcode
    PicMidrangeOpcode opcode = pic_midrange_get_opcode(instr);
    if (opcode == PIC_MIDRANGE_OPCODE_INVALID) {
        return NULL;
    }

    // get opargs
    PicMidrangeOpArgs opargs = pic_midrange_get_opargs(instr);

    // uplift
    PicILUplifter uplifter = pic_midrange_il_uplifters[opcode];
    if (uplifter) {
        return uplifter(opargs, instr);
    }

    // return NULL on failure
    return NULL;
}
