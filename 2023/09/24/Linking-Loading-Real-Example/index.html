Linking & Loading - Real Example

Posted on Sun, 24th September, 2023 In linking , loading Disqus:

Background

I’ve started writing the binary parser module for AnvieLabs. In the pursuit of better understanding relocation process while loading and linking of binary files. This would help me gain better understanding of how symbols and sections .got, .plt, .got.plt, .plt.got work. In this process, I find myself reading Linkers & Loaders by John R. Levine. Thanks to him for this super awesome, very detailed book.

I encountered this real life example in Chapter 1 of this book that helps explaining the linking process by giving example of how the relocation and symbol resolution works. This post is covering the exact sample code but compiled by me. There’s nothing special about this post other that the example and me verifying what the author writes!

Code

Let’s take a look at the sample code and compile them to their object files. I’ll also give you the commands, so, you too can verify this example.

There are two source files :

  • a.c, containing a single function void a(char* s). This will print the given string to stdout.
  • m.c containing the void main(int ac, char** av) and using the a function declared in a.c src file.
  • a.c
  • m.c

Compiling To Object Code

We’ll first compile each of the above source file to their respective object file using the command gcc -c a.c -o a.o && gcc -c m.c -o m.o. This will create a.o as object code for a.c and m.o for m.c.

Objdump & Verifying The Content

To check the assembled code and relocation and other info, we’ll use objdump with the following command : objdump -x -d -Mintel,intel-mnemonic,addr64 m.o. This will disassemble m.o with other information like segments, symbols, etc…

Let’s see the output

  • a.o
  • m.o

The following information is concluded :

  • If an unknown symbol is used that is defined in a different library, then offset to a new undefined symbol is provided.
  • If symbol is defined in the same file then direct offset to it is provided.
  • In object files, virtual address is not provided and whole binary seems to be mapped at address 0. Obviously this calls for later address resolution in linking phase as almost all systems treat address 0 as NULL pointer.

Linking & Creating Final Code

Linking with ld can be complex, so I’ll just use gcc to link these two object code and create the final executable using the command : gcc -o m m.o a.o

Alright, time to look at the linked and resolved code :

  • It’s interesting to see that many of the added sections/segments were not present in the the raw object code.
  • There are still some undefined symbols in linked executable.
  • External symbols present in dynamic libraries are moved to plt (Program Linkage Table) like write@plt and strlen@plt.
  • Symbols in a.o and m.o are directly used in final executable
